ProTanki Commander

A lightweight Windows tool that runs 6–10 ProTanki accounts on one VPS. It watches every game window, clicks Play as soon as a battle opens, checks that each click landed, and pulls every account out at once on one key press. This page covers the research, the architecture, the code-level techniques, the build plan and the demo plan.

01Overview in 60 seconds

Read this first. Everything after it is detail.

Plain English

Picture 10 ProTanki windows laid out in a grid on one screen, like security-camera monitors. Our program is a robot supervisor that looks at all 10 windows about 20 times a second.

When it sees the green Play button light up in a window, it clicks it straight away, without moving your real mouse. Then it looks again to make sure the click worked, and clicks again if it didn't.

When you press Ctrl+Alt+X, or the big red button, or send /exitall from Telegram, the supervisor tells every window to leave the battle at the same moment. Any window that doesn't respond gets closed by force.

All button positions are saved in "presets" that you set by clicking on the game window. Nothing is hard-coded.

  1. Launch. The tool starts one ProTanki client per account. Each runs from its own copy of the game folder, because the game's runtime (Adobe AIR) refuses to run twice from the same copy. Each window gets a fixed size and a fixed slot in a grid.
  2. Watch. 20–25 times a second, the tool takes one screenshot of the desktop. It cuts out the small region around each window's important button and compares a few pixel colours to what the preset expects. That takes microseconds.
  3. Act. When a window's "Play is ready" trigger fires, the tool sends a mouse-click message directly to that game window (Windows PostMessage). The real cursor doesn't move, no focus is needed, and all 10 windows can be clicked in the same few milliseconds.
  4. Verify. 100–200 ms later it checks whether the screen changed as expected (we're in battle). If not, it retries. If that keeps failing, it switches that account to "real mouse" mode and logs or alerts.
  5. Exit. One global trigger moves every account into EXITING at the same moment: exit clicks, then window close, then force-kill after 2 s.
  6. Survive. A watchdog notices crashed clients, lost windows and stuck screens, and relaunches or recovers them. The VPS scripts keep the screen rendering after you close or minimize Remote Desktop.

Key insight: "queue" is ambiguous

ProTanki has no matchmaking queue CONFIRMED. It has a battle list, and joinable battles show a green Play button. So "join when the queue opens" probably means one of these:

  • (a) a battle with free slots appears, or the Play button lights up;
  • (b) a gold-box drop is announced ("Gold Box will be dropped soon" plus a siren) and they want every account in the battle;
  • (c) a specific battle (maybe a private link) opens.

The design handles all three, because a "trigger" is just a visual condition you define. Asking this question in the proposal shows we understand the game.

Why would someone want this?

INFERRED The most likely reasons:

  • Fill a battle with your own accounts to raise your odds of catching a gold box. These are worth 1,000 crystals by default, 2,000–5,000 in events, and up to 100,000 at the 2026 anniversary.
  • Collect battle-fund payouts.
  • Avoid the 5-minute AFK kick.

The "exit all instantly" part fits taking the reward and leaving before anyone reacts. We don't need to know why, but it explains the focus on speed.

Terms of service

Using this tool breaks ProTanki's game rules. That is the client's risk. We build no detection-evasion features, never market it as "undetectable", and put one neutral line about it in the proposal.

For our own demo, use throwaway accounts, because those accounts could be banned.

Protocol reverse-engineering exists, and we don't use it

Community projects have reverse-engineered the network protocol: ProtankiNetworking (C#), ProboTanki-Lib (Python), protanki-protocol-rs (Rust, with a headless client). A packet-level bot would be faster, but it is fragile (the client is getting more obfuscated), much harder to build, and far more clearly "cheating".

The client asked for a clicker, so we stay at the UI level. It's simpler, safer, and easy to explain.

04The 6 hard problems

Anyone can write an autoclicker. These six problems are what separate a tool that works on a VPS with 10 accounts from one that doesn't.

① Ten copies of one game

Problem: Adobe AIR allows only one instance per application ID C. Double-clicking ProTanki.exe a second time just brings the first window forward.

Solution: one copy of the install folder per account, with a unique <id> in META-INF\AIR\application.xml. The community launcher does exactly this. → §12

② Clicking 10 windows at once

Problem: a normal autoclicker moves the mouse, and there is only one mouse. Clicking 10 windows that way means switching focus 10 times, which takes about 0.5–1 s.

Solution: send the click as a window message straight to each game window (PostMessage). The cursor doesn't move, no focus is needed, and it's parallel. The fallback is real input, one window at a time. → §9

③ Seeing 10 windows cheaply

Problem: taking 10 screenshots, 20 times a second, and analysing whole frames would burn the VPS CPU.

Solution: windows are tiled with no overlap. Each tick takes one desktop grab, slices a tiny region per window with numpy, and compares 3–5 pixels. That costs microseconds per window. → §10

④ The Remote Desktop trap

Problem: on a VPS, if you minimize or close the Remote Desktop window, Windows stops drawing the desktop. Screenshots come back black and real-mouse input fails. Most clickers die here.

Solution: a registry fix for "minimized", a tscon disconnect script for "closed", and a forced resolution at startup. → §16

⑤ Coordinates that don't drift

Problem: different window sizes, DPI scaling (125%/150%) and title-bar heights all shift where a button is on screen.

Solution: the tool is DPI-aware, every window gets a fixed client size, and positions are stored as ratios of the client area. → §11

⑥ "Without missing actions"

Problem: a click sent isn't a click received. The game may be lagging, a menu may cover the button, or the window may have crashed.

Solution: verify after every click, retry with backoff, escalate to real input, run a watchdog that relaunches, and log every click. → §14

Why one "brain" thread instead of 10 worker threads?

With 10 threads, each one would take its own screenshot, and they'd compete for the CPU and for the single mouse. With one brain we take one screenshot per tick and make every decision from it. That's cheaper, it's predictable, and the log reads like a story.

Sending a posted click takes microseconds, so doing all 10 inline is effectively simultaneous.

07The engine tick loop

What happens in each 40 ms tick, and how fast we react.

Figure 2: Time budget for one tick. Capture time depends on the region size; it gets measured in Phase 0.

app/engine.py (sketch)
class Engine(threading.Thread):
    def run(self):
        while not self.stop.is_set():
            t0 = time.perf_counter()
            self._drain_commands()                     # START/STOP/EXIT_ALL from the bus
            frame = self.capture.grab(self.active_rois())  # ONE grab for all accounts
            now = time.monotonic()
            for acc in self.accounts:
                try:
                    obs = self.triggers.evaluate(acc, frame)   # {"join_ready": True, ...}
                    for action in acc.fsm.step(obs, now):    # state machine decides
                        self.dispatcher.submit(acc, action)    # post = instant, sendinput = queued
                except Exception:
                    log.exception("acc %s failed this tick", acc.id)  # one bad account never kills the loop
                    acc.fsm.fault()
            self.watchdog.check(self.accounts, now)
            elapsed = time.perf_counter() - t0
            self.stop.wait(max(0.0, self.poll_s - elapsed))     # sleep, but wake instantly on stop
Debounce trade-off

Requiring the trigger in 2 consecutive frames removes false positives, such as an animation flashing green. It costs one tick (about 40 ms) of latency.

For join_ready, speed matters most, so the default is 1 frame with a multi-pixel check: 3–5 sample points that must all match. That is nearly as safe and has no extra delay. It's configurable per trigger with "debounce": 1|2.

class AccountFSM:
    def step(self, obs: dict, now: float) -> list[Action]:
        if EXIT_ALL.is_set() and self.state not in (S.EXITING, S.CLOSING, S.EXITED):
            return self._enter(S.EXITING, now)              # top priority, from any state
        match self.state:
            case S.WATCH if obs["join_ready"]:
                return self._enter(S.JOIN, now)                # returns [Click("play_btn")]
            case S.JOIN:
                if obs["in_battle"]:      return self._enter(S.IN_BATTLE, now)
                if self._verify_due(now):  return self._retry_or_fail(now)  # re-click, backoff, escalate
                if self._timed_out(now):   self.misses += 1; return self._enter(S.WATCH, now)
            case S.IN_BATTLE:
                if obs["lobby"]:          return self._enter(S.LOBBY, now)
                if self._afk_due(now):     return self.seq("anti_afk")
            # ... LAUNCH / LOGIN / LOBBY / EXITING / CLOSING
        return []

09Clicking: the input layer

There are two ways to "click" in Windows. We build both and pick one per account.

Plain English

Windows tells every program "the mouse was pressed at x,y" by putting a message in that program's mailbox. A normal autoclicker moves the real mouse and lets Windows deliver the message to whatever window is on top.

We skip that and drop the "mouse pressed here" message directly into each game window's mailbox. The game can't tell the difference (usually), your mouse stays still, and we can do it for 10 windows at the same moment.

The "deepest child" detail

Game windows are often nested, for example a frame window containing a content window. The message has to go to the innermost window under the point, with coordinates converted into that window's space. Send it to the outer frame and the game never sees it. This is the most common reason background clicks "don't work".

app/win/input_post.py
import win32gui, win32con, win32api

FLAGS = win32con.CWP_SKIPINVISIBLE | win32con.CWP_SKIPDISABLED

def deepest_child(top: int, x: int, y: int) -> tuple[int, tuple[int, int]]:
    """Walk down to the innermost child window at client point (x, y) of `top`."""
    hwnd, pt = top, (x, y)
    while True:
        child = win32gui.ChildWindowFromPointEx(hwnd, pt, FLAGS)
        if not child or child == hwnd:
            return hwnd, pt
        sx, sy = win32gui.ClientToScreen(hwnd, pt)         # parent-client → screen
        pt = win32gui.ScreenToClient(child, (sx, sy))       # screen → child-client
        hwnd = child

def post_click(top: int, x: int, y: int, hold_ms: int = 0) -> None:
    hwnd, (cx, cy) = deepest_child(top, x, y)
    lp = win32api.MAKELONG(cx, cy)
    win32gui.PostMessage(hwnd, win32con.WM_MOUSEMOVE, 0, lp)               # some engines need hover first
    win32gui.PostMessage(hwnd, win32con.WM_LBUTTONDOWN, win32con.MK_LBUTTON, lp)
    if hold_ms: time.sleep(hold_ms / 1000)                               # optional 10–30 ms if ignored
    win32gui.PostMessage(hwnd, win32con.WM_LBUTTONUP, 0, lp)

def post_key(top: int, vk: int) -> None:
    scan = win32api.MapVirtualKey(vk, 0)
    win32gui.PostMessage(top, win32con.WM_KEYDOWN, vk, 1 | (scan << 16))
    win32gui.PostMessage(top, win32con.WM_KEYUP,   vk, 1 | (scan << 16) | (0xC0 << 24))
If AIR ignores posted clicks, try these in order before falling back
  1. SendMessage instead of PostMessage. It is synchronous, and Chromium uses it internally.
  2. Send WM_ACTIVATE(WA_ACTIVE) and WM_SETFOCUS to the window first. Many engines drop input when they think they're inactive.
  3. Add a 10–30 ms gap between down and up.
  4. Send to the top-level window instead of the child (the opposite of the usual rule).
  5. If all of these fail, the account uses input_mode: "sendinput".

The spike script in Phase 0 runs all five variants and prints which ones worked.

app/win/input_send.py (fallback, serialized)
_input_lock = threading.Lock()     # ONE real mouse → strictly one window at a time

def sendinput_click(top: int, x: int, y: int) -> None:
    sx, sy = win32gui.ClientToScreen(top, (x, y))
    with _input_lock:
        prev_fg, prev_pos = win32gui.GetForegroundWindow(), win32api.GetCursorPos()
        force_foreground(top)                      # AttachThreadInput trick + SetForegroundWindow
        _send_abs_move(sx, sy)                     # SendInput MOUSEEVENTF_MOVE|ABSOLUTE|VIRTUALDESK (0..65535)
        _send(MOUSEEVENTF_LEFTDOWN); time.sleep(0.012); _send(MOUSEEVENTF_LEFTUP)
        win32api.SetCursorPos(prev_pos); force_foreground(prev_fg)
Gotchas
  • UIPI: if the game runs as Administrator, the tool must too. Otherwise Windows silently drops our messages and input. Rule: run both at the same level.
  • Foreground lock: SetForegroundWindow is refused unless the caller "owns" the input. The standard workaround is AttachThreadInput to the foreground thread, or sending a harmless ALT key press first.

10Seeing: capture & triggers

How a pile of pixels becomes "Play button is ready in window 4".

Plain English

We never "read" the game. We look at it, the way you would.

For each window, the preset says something like: "at 84% across and 90% down, the pixel should be this shade of green when Play is clickable". Every tick we check a few such pixels. If they all match within a tolerance, the trigger is true.

For harder cases we compare a small saved picture, such as the battle HUD, against a region of the window. That is template matching.

Capture strategy

  1. Primary: the windows are tiled with no overlap and are never minimized, so what's on the desktop is each window's content. One mss grab of the bounding box of all active regions, then numpy slicing per account. Alternatively, one tiny grab per region when the regions are few and small (each is about 1 ms).
  2. Fallback: PrintWindow(hwnd, hdc, PW_CLIENTONLY | PW_RENDERFULLCONTENT) per window. It works for covered windows. Without flag 2, GPU-composited windows come back black. It costs about 5–20 ms per call, so limit it to about 5–10 Hz per window.
  3. Optional: Windows Graphics Capture (windows-capture / zbl) or dxcam (DXGI) on machines with a GPU. These are faster but need a live console session.
app/win/capture.py
import mss, numpy as np

class DesktopCapture:
    def __init__(self):
        self.sct = mss.mss()

    def grab(self, rois: dict[str, tuple[int,int,int,int]]) -> dict[str, np.ndarray]:
        """rois: {acc_id: (left, top, right, bottom)} in SCREEN coords → {acc_id: BGRA array}"""
        if not rois: return {}
        L = min(r[0] for r in rois.values()); T = min(r[1] for r in rois.values())
        R = max(r[2] for r in rois.values()); B = max(r[3] for r in rois.values())
        shot = np.asarray(self.sct.grab({"left": L, "top": T, "width": R-L, "height": B-T}))
        return {a: shot[t-T:b-T, l-L:r-L] for a, (l, t, r, b) in rois.items()}   # zero-copy views

app/triggers.py
def pixel_match(img: np.ndarray, x: int, y: int, rgb: tuple, tol: int) -> bool:
    patch = img[max(y-1,0):y+2, max(x-1,0):x+2, :3].reshape(-1, 3).mean(axis=0)  # BGR mean of 3×3
    b, g, r = patch
    return max(abs(r-rgb[0]), abs(g-rgb[1]), abs(b-rgb[2])) <= tol    # Chebyshev distance

def template_match(img, tmpl_gray, region, thr) -> bool:
    roi = cv2.cvtColor(crop(img, region), cv2.COLOR_BGRA2GRAY)
    return cv2.minMaxLoc(cv2.matchTemplate(roi, tmpl_gray, cv2.TM_CCOEFF_NORMED))[1] >= thr
Keeping the CPU low with 10 windows
  • Only grab regions the current state needs. WATCH needs the Play button region. IN_BATTLE needs only a small HUD patch, checked at 2–5 Hz.
  • Load template images once, at startup, in greyscale.
  • Never call GetPixel in a loop. Each call is a separate round-trip to Windows' drawing system and is very slow.
  • The loop sleeps for the rest of each tick and never spins.

Expected cost is a few percent of one core for 10 accounts. The 10 game clients will use far more CPU than our tool.

11Coordinates, DPI & tiling

How one preset stays correct across 10 windows, different VPSs and display scaling.

Three coordinate spaces

  • Screen space: pixels from the top-left of the desktop. Used for capture and SendInput.
  • Client space: pixels from the top-left of the game's drawable area, excluding the title bar and borders. Used for PostMessage.
  • Ratio space (what presets store): x/client_w, y/client_h, both 0..1. The same numbers work for every window size.
# preset → this window
cw, ch = client_size(hwnd)                # GetClientRect
cx, cy = round(rx * cw), round(ry * ch)   # ratio → client
sx, sy = ClientToScreen(hwnd, (cx, cy))   # client → screen (capture)

# picker → preset
cx, cy = ScreenToClient(hwnd, cursor)
rx, ry = cx / cw, cy / ch

Example: Play is at client (539, 434) in a 640×480 window, so the ratio is (0.842, 0.904). In an 800×600 window that becomes (674, 542).

DPI awareness: the silent killer

If the VPS runs at 125% or 150% scaling and our process is not DPI-aware, Windows lies to us. It "virtualizes" coordinates, so every click lands in the wrong place. The fix is the very first line of main.py:

import ctypes
ctypes.windll.user32.SetProcessDpiAwarenessContext(ctypes.c_void_p(-4))   # PER_MONITOR_AWARE_V2

Tiling at an exact client size

A window's outer size includes the title bar and borders, which vary by theme. To get exactly 640×480 of game area, ask Windows how big the outer frame must be:

def place_client(hwnd, x, y, cw, ch):
    style   = user32.GetWindowLongW(hwnd, GWL_STYLE)
    exstyle = user32.GetWindowLongW(hwnd, GWL_EXSTYLE)
    rc = RECT(0, 0, cw, ch)
    user32.AdjustWindowRectExForDpi(byref(rc), style, False, exstyle, user32.GetDpiForWindow(hwnd))
    user32.SetWindowPos(hwnd, None, x, y, rc.right-rc.left, rc.bottom-rc.top,
                        SWP_NOZORDER | SWP_NOACTIVATE)

To test in Phase 0

TEST Does ProTanki's content scale with the window (Flash StageScaleMode), or does it reflow or crop at fixed pixel sizes?

  • If it scales, ratio coordinates just work.
  • If it doesn't, we enforce one identical client size for all windows. Ratios still work then, because every window is the same size.

We also need the minimum usable size. For tiling 10 windows on 1920×1080, the ideal is about 470×350 each.

12Running 10 clients at once

How we get around Adobe AIR's "one instance per app" rule.

Plain English

Adobe AIR checks the app's ID card (an ID string inside a file called application.xml). If a copy with that ID is already running, it refuses to start another one.

So we give each account its own copy of the game folder with a different ID card: ProTanki.acc1, ProTanki.acc2, and so on. Windows then treats them as 10 different apps. It costs disk space (about 100–400 MB per copy), which is fine on a VPS.

tools/clone_install.py (sketch)
SRC = Path(r"C:\Program Files (x86)\ProTanki Online")

def clone(acc_id: str, dst_root=Path(r"C:\ProTanki")) -> Path:
    dst = dst_root / acc_id
    shutil.copytree(SRC, dst, dirs_exist_ok=True)
    xml = dst / "META-INF" / "AIR" / "application.xml"
    txt = xml.read_text(encoding="utf-8")
    txt = re.sub(r"<id>([^<]+)</id>", lambda m: f"<id>{m.group(1)}.{acc_id}</id>", txt, count=1)
    xml.write_text(txt, encoding="utf-8")
    return dst / "ProTanki.exe"

13Exit All

The feature the client cares about most. It has several layers, starts with the fastest, and always ends with a guarantee.

Figure 4: Exit All timeline. Phase A finishes in well under 1 s for all accounts. B and C only run for windows that didn't respond, or when the mode is "close client".

exit_modeBehaviourUse when
leave_battle (default)Run the exit sequence in every window, then verify the lobby is showingLeave fast, keep clients open for the next round
close_clientExit sequence → WM_CLOSE → kill after 2 s"Get out of everything, now"
killpsutil.kill() on every tracked PID immediately (TerminateProcess)Panic button. The server sees each connection drop within milliseconds.
 
def exit_all(self, mode="leave_battle"):
    t0 = time.perf_counter()
    EXIT_ALL.set()                                        # every FSM sees it on its next step / wait
    if mode == "kill":
        procs = [psutil.Process(p) for a in self.accounts for p in a.pids if psutil.pid_exists(p)]
        for p in procs: p.kill()
        psutil.wait_procs(procs, timeout=2)
    else:
        for a in self.accounts:                          # all posted in the SAME loop → parallel
            self.dispatcher.run_sequence(a, "exit", priority=True)
    log.info("EXIT_ALL dispatched to %d accounts in %.1f ms", len(self.accounts), (time.perf_counter()-t0)*1000)
Why this is "instant"
  • The trigger is a threading.Event, so there's no polling delay.
  • Posted messages to 10 windows take about 1 ms in total.
  • The only real delay is the game showing its exit menu (~100–300 ms).
  • Every wait inside a sequence uses EXIT_ALL.wait(timeout) instead of sleep. So an account in the middle of a join sequence aborts immediately instead of finishing its clicks.

14Reliability & watchdog

How we back up "without missing actions" and "without crashing".

Verify-after-click loop

  1. Click → record t_click and the expected outcome (in_battle, or not join_ready).
  2. After 80–200 ms, check the outcome on the next frames.
  3. No change → re-click, with backoff of 150, 300, then 600 ms.
  4. 3 failures → escalate: switch that account to sendinput, retry once, then raise an alert.
  5. The guard rule: never click Join unless join_ready is true now. That makes clicks safe to repeat, so they never double-act.

Watchdog (every tick, very cheap)

  • psutil.pid_exists(pid) is false → the client crashed → relaunch.
  • IsWindow(hwnd) is false → the window is lost → re-find it by PID or title.
  • The window was moved or resized → re-tile.
  • IsIconic(hwnd) (minimized) → restore it with SW_SHOWNOACTIVATE.
  • The state hasn't changed for N seconds when it should have → run the recover sequence (Esc, go to lobby).
  • The capture frame is all black → the desktop isn't rendering → RDP warning in the UI and on Telegram.

Fault isolation

  • Each account's step is wrapped in try/except. One bad account can't stop the others.
  • The engine thread restarts itself if it dies, with a supervisor in main.py.
  • The UI only reads a state snapshot, so a UI freeze never blocks clicks.

Logging & evidence

  • Rotating file logs/YYYY-MM-DD.log.
  • One line per action: 12:00:01.234 acc3 JOIN click play_btn (539,434) post lat=63ms ✓
  • When a verify fails, the region is saved as a PNG in logs/fail/. You can see exactly what the tool saw.
  • Counters per account: clicks, joins, misses, average reaction time.

16VPS operations

The section that shows the client we've actually run automation on a VPS before.

The trap

A Windows VPS only "draws" its desktop while someone is looking.

  • Minimize the Remote Desktop window: the session drops into a GUI-less mode. Screenshots come back black and SendInput fails.
  • Close Remote Desktop: the session is locked, with the same result.

Posted clicks still arrive, but we can no longer see anything, so triggers never fire. The tool looks like it "randomly stops working at night".

Fix 1: Minimized RDP window (run on the client's own PC, not the VPS)

[HKEY_CURRENT_USER\Software\Microsoft\Terminal Server Client]
"RemoteDesktop_SuppressWhenMinimized"=dword:00000002

[HKEY_LOCAL_MACHINE\SOFTWARE\Microsoft\Terminal Server Client]
"RemoteDesktop_SuppressWhenMinimized"=dword:00000002

[HKEY_LOCAL_MACHINE\SOFTWARE\Wow6432Node\Microsoft\Terminal Server Client]
"RemoteDesktop_SuppressWhenMinimized"=dword:00000002

Then reconnect. You can now minimize the RDP window and the VPS keeps rendering.

Fix 2: Leaving without locking (run on the VPS as Administrator, instead of clicking ✕)

vps/Disconnect-Keep-Running.bat
@echo off
:: Moves this RDP session to the console: stays unlocked and keeps rendering.
:: "query user" line while connected:  >username  rdp-tcp#0  2  Active ...  → token 3 = session ID
for /f "skip=1 tokens=3" %%s in ('query user %USERNAME%') do (
  %windir%\System32\tscon.exe %%s /dest:console
)

This works while you're connected, because the active RDP session has a session name, so the ID is token 3. The tool also ships a PowerShell version that parses the columns by header. We confirm it on the client's Windows Server version in Phase 4.

Fix 3: Console resolution

After tscon, the console often falls back to 1024×768, which breaks the 10-window grid. Options:

  • The tool calls ChangeDisplaySettingsEx at startup to force 1920×1080, or whatever layout needs.
  • Optionally install Virtual Display Driver (winget install --id=VirtualDrivers.Virtual-Display-Driver -e) for a permanent virtual monitor.
  • Most robust: run a VNC server attached to the console, plus Sysinternals Autologon. Then RDP is only used for setup.

18Hotkey & remote triggers

Ways to fire Exit All, from any context.

app/win/hotkeys.py
import ctypes, ctypes.wintypes as wt
user32 = ctypes.windll.user32
MOD_ALT, MOD_CONTROL, MOD_NOREPEAT, WM_HOTKEY = 0x1, 0x2, 0x4000, 0x0312

def hotkey_thread(bus):
    user32.RegisterHotKey(None, 1, MOD_CONTROL | MOD_ALT | MOD_NOREPEAT, ord("X"))   # EXIT ALL
    user32.RegisterHotKey(None, 2, MOD_CONTROL | MOD_ALT | MOD_NOREPEAT, ord("K"))   # KILL ALL
    user32.RegisterHotKey(None, 3, MOD_CONTROL | MOD_ALT | MOD_NOREPEAT, ord("P"))   # PAUSE ALL
    msg = wt.MSG()
    while user32.GetMessageW(ctypes.byref(msg), None, 0, 0) > 0:              # blocks, 0% CPU
        if msg.message == WM_HOTKEY:
            bus.put({1: "EXIT_ALL", 2: "KILL_ALL", 3: "PAUSE_ALL"}[msg.wParam])

26Glossary

TermPlain-English meaning
HWND"Window handle": Windows' ID number for a window. Everything we do to a window uses it.
PIDProcess ID: Windows' ID number for a running program. We use it to find its window and to kill it.
PostMessageDrops a message (such as "mouse pressed at x,y") into a window's mailbox without waiting. It's how we click without moving the mouse.
SendInputSimulates the real mouse or keyboard. It only reaches the window in front.
Client areaThe inside of a window, where the game draws, excluding the title bar and borders.
ROI"Region of interest": the small rectangle of pixels we actually check.
TriggerA yes/no question answered from pixels, e.g. "is the Play button green?"
Template matchingFinding a small saved picture inside a bigger image (OpenCV).
DebounceRequiring a signal twice in a row before acting, to ignore flickers.
State machineA model where each account is in one named state and moves between states by clear rules.
TickOne cycle of the engine loop (about every 40 ms).
DPI awarenessTelling Windows "give me real pixels" so display scaling doesn't distort coordinates.
Adobe AIRAdobe's desktop runtime for Flash apps. ProTanki's Windows client runs on it.
App IDAIR's unique name for an app. Only one instance per ID can run, which is why we clone.
tsconA Windows command that moves a Remote Desktop session to the physical "console", so it stays unlocked and drawing.
UIPIA Windows security rule: a normal program can't send input to an Administrator program.
Nuitka / PyInstallerTools that turn a Python program into a Windows .exe, so Python doesn't need installing.
WatchdogA background check that notices crashes or stuck states and fixes them.
